# Local demo data

Run the database migrator with `--seed-demo` when you want a populated **local test tenant**. The normal migrator command applies migrations and module seeders; the extra flag adds connected business examples after those steps.

```powershell
.\scripts\migrate-tenant.ps1 -TenantId dev -SeedDemo
```

Run the command from `simpliadz-runner`. Use `-TenantId demo` to populate the separate `demo` database instead. The flag is explicit so ordinary migrations do not add sample customers, sales, or expenses to a tenant. It does not reset the database. The seeder checks existing fixtures and preserves records changed through the API; rerunning it does not add another copy of the same sample sale, receipt, expense, or work session.

## What the seeder creates

The ordinary module seeders already provide the local Admin user, permissions, two locations (`MAIN`, `WH`), brands, categories, Size and Color attributes, products and variants, DZD price lists, opening stock, and standard barcode and inventory document templates. `--seed-demo` adds:

| Area | Test data |
| --- | --- |
| Identity | Demo Cashier, Demo Manager, and Demo HR roles and users. Manager receives business permissions; HR receives user and worked-hours permissions. |
| Organization | An organization profile if absent, plus one completed cashier work session. Existing organization settings are not overwritten. |
| Inventory | Old low stock at `MAIN`, draft and cancelled transfers, counts with and without a recorded variance, an unlabelled cap, unused attribute values, an inactive location, and inactive barcode and stock document templates. |
| Purchasing | Demo supplier, draft PO, ordered PO ready for receiving, and a partially received PO with an immutable goods receipt and matching stock movement. |
| Sales | Retail and wholesale customers, two registers, an open cash session, a draft sale, and a completed paid sale with line and sale discounts and a matching stock movement. The completed sale can be used to test returns. |
| CRM | A DZD loyalty program, one demo gift reward, and a card for the demo sale customer. The card starts at zero points because the sample sale predates enrollment. Complete a new named sale to test earning. |
| Accounting | Rent and utilities categories, plus one dated shop expense. |
| Reporting | 336 dated paid sales over 84 days at Main Store and Demo East Shop, with multiple products, cash/card payments, discounts, recorded cost and partial/full refunds. Weekly expenses support shop comparison, gross profit and operating contribution. |
| Audit | A demo seed entry so audit history has an example. |

Notifications remains a scaffold and has no business data to seed. Enabled modules are checked for the selected tenant; disabled modules are skipped.

Inventory warning records are generated by the API's scheduled scan after it starts, or immediately through the authorized `POST /inventory-warnings/run` endpoint. The demo seeder prepares an old, low-stock variant and enables the schedule when the demo warning settings have not been used yet.

For dashboard testing, select a range covering the past three months and compare all shops with Main Store and Demo East Shop individually. For POS pricing, select the demo wholesale customer in a retail ticket and check that the price remains the retail price. For reactivation, use Demo Closed Shop, Demo Archived Label, or Demo Archived Stock List. Use Demo Packaging to exercise editing and deleting unused attribute values.

## Demo sign-ins

New demo users receive `Demo123!` as their initial password:

| Role | Email |
| --- | --- |
| Cashier | `cashier.demo@local.test` |
| Manager | `manager.demo@local.test` |
| HR | `hr.demo@local.test` |

The existing local Admin account remains `admin@dev.local` / `Admin123!` on a fresh tenant. Re-running the seeder does **not** reset passwords for existing users. These credentials and fixtures are intended only for local testing.

After seeding, start the API as described in [Run the backend locally](LOCAL_START_GUIDE.md). The API's active tenant must match the tenant you seeded; no `X-Tenant-Id` header is required. Browse [the MVP feature checklist](../../features.md) for routes to exercise.
